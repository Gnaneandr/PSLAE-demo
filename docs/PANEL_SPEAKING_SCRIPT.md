# PANEL_SPEAKING_SCRIPT (about 20 minutes; commands in brackets)
**1. The problem.** "Machines in a factory must authenticate each other over a wireless link an attacker can read and edit, using only cheap operations. The base paper proposes PSLAE: two messages built from XOR, hashes and one lightweight authenticated encryption."
**2. System model.** [`python demo.py overview`] "A sensor (6LN) and a controller (6LC). Each has secrets from a one-time registration. Public on the air: timestamps, random numbers, the masked alias D, ciphertexts and tags."
**3. Registration.** [`python demo.py registration`] "The controller creates the sensor's keys and alias. The paper has two inconsistencies here: a '265-bit' master secret and a 256-bit hash that does not exist in SHA-1, so the audited project extends SHA-1 (H_bits) - that is a reconstruction."
**4. AKE1 / AKE2 / AKE3.** [`ake1`, `ake2`, `ake3`] "M1: the sensor hides its alias and sends it with a tag. The controller checks time, alias, tag and consistency, then builds the key and M2. The sensor verifies M2 and derives the same key. In AKE3 the paper's equation cannot be executed (it needs ID6LC), so the sensor reads Sc1 from the encrypted block."
**5. Session key.** [`session-key`] "SK = SHA-1(AID‖B1‖Sc1‖RN1‖RN2). It is never sent; M = SHA-1(SK) lets the sensor check agreement."
**6. Sizes.** [`packet-breakdown`] "M1 is 416 bits, matching the paper. M2 is 576 bits with the paper's stated widths; the reconstructed configuration shows 608 only because its timestamp is 64 bits, which the paper does not say. We report both."
**7. Cryptographic operations.** [`operations`] "XOR masks, SHA-1 fingerprints, AES-CTR hides, HMAC authenticates. We measured 12 hash operations in the AKE phase; the paper counts 8 and the audited script had a constant 8."
**8. Attackers.** [`security --scenario A01`, `A04`, `A05`, `A03`, `A17`, `A11`] "Replay, bit flips and forged tags are rejected. But a held message with a refreshed timestamp is accepted and desynchronises the pair; one lost reply locks the sensor out; and the two ciphertexts of one session leak the alias because they share key and nonce. We report these as weaknesses, not as passes."
**9. Scyther and SVO.** [`scyther`, `svo --summary`] "Scyther finds no attack in our model - 10 claims Ok - but that model authenticates the timestamps, which the paper does not, and XOR is abstracted. So it is a result for our reconstruction. The SVO derivation is manual; G2 is our reconstruction and G1's published steps do not strictly follow."
**10. Performance and storage.** [`performance --part summary`] "Paper and measured numbers side by side. Sensor: 32 bytes are actually read, 40 are stored. Controller record: 60 bytes stored including 4 bytes of non-functional padding."
**11. Discrepancies and reconstructions.** [docs/PAPER_VS_IMPLEMENTATION.md] "Twenty rows: what the paper says, what our code does, and whether it is literal, reconstructed or a discrepancy."
**12. What is verified and what is not.** "Verified by running: both parties derive equal keys; the listed attack inputs are rejected or accepted exactly as shown; 202 automated tests pass. Not verified: that this is the authors' design (their code is unpublished), ACE itself, Windows execution, any property beyond the tested scenarios, and a machine-checked SVO proof."
