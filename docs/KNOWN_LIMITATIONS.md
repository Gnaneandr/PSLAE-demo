# KNOWN_LIMITATIONS (honest list)
1. **ACE is not implemented.** The cipher is an interface-level stand-in (AES-128-CTR + HMAC-SHA256/128). Nothing here supports claims about the authors' ACE (security, energy, speed).
2. **H_bits is not in the paper.** The 256-bit hash values the paper's equations need are produced by a SHA-1 counter-mode extension. SHA-1 itself is collision-weakened; a 160-bit SK is what the paper's accounting implies.
3. **The implementation is a reconstruction, not the authors' code.** The paper's code is unpublished; the audited project made the documented choices R1-R12 (see `docs/RECONSTRUCTION_DECISIONS.md`). Nothing here shows that it behaves like the authors' implementation.
4. **The 608-bit M2 / 1024-bit total depend on a 64-bit T6C** that contradicts the paper's 32-bit statement. Both figures are reported; the paper's targets are not endorsed.
5. **Operation counts:** the measured number of logical hash operations in the AKE phase is 12. The paper counts 8, and the audited `performance/overhead.py` hard-codes 8, so its "match" is not supported by measurement. The paper's "2 ACE" is a counting convention (one per message); 4 AEAD operations are actually executed.
6. **Storage:** the audited record stores a 4-byte non-functional `_reserved` pad; the sensor object also stores `id6ln`, which AKE never reads. Stored, used and Python-object sizes are reported separately.
7. **Attack lab shows weaknesses, not proofs.** A REJECT means the tested input was rejected. Found weaknesses: timestamps T6LN/T6C are unauthenticated (A03a held-message attack -> desynchronisation; A06); one-sided freshness check (A02c); loss of M2 permanently desynchronises (A11b, no timeout or recovery); M1 and M2 share key, nonce and AD, so one session leaks AID6LN/TID6LC (A17). Replay protection comes from the state update, not from a replay cache (the `seen_*` sets exist but are unused).
8. **Malformed-length messages** are rejected by unhandled `ValueError`, not by explicit validation.
9. **Scyther:** XOR is abstracted; timestamps are variables; state updates, key reuse and desynchronisation are not modelled; bounded to 100 runs. The 10 Ok results depend on binding the timestamps into the authenticated part of the model, which the paper does not do (the paper's own model is unpublished), so they do not show that the protocol exactly as written passes. The Windows Scyther binary was not tested.
10. **SVO:** manual derivation, not machine-verified. G1 is the paper's published derivation, which does not follow strictly from its listed premises; G2 is a reconstruction.
11. **Deterministic demo randomness** (seeded SHA-256 generator) is for repeatable teaching only; never use it for real keys. `--random` uses os.urandom.
12. **Timing numbers** are wall-clock on the machine used and are not comparable with the paper's modelled 0.411 ms.
13. **Windows commands were not executed** (no Windows host); everything else was run on Linux in a clean virtual environment.
14. **Instrumentation** wraps the real functions at run time (monkey-patching) to record sizes; it never alters their return values (checked by comparing instrumented and recomputed values in each stage).
